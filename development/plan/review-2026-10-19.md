# Review findings for PolarBookshop

Findings from a review of `mikkosuonio/development` from fb268d7 up to 191a277, with proposed
fixes, in priority order. File paths are relative to `PolarBookshop/` unless they start with
`development/` or `.github/`.

## Summary

Four findings are High. Three are application bugs that lose data or hide outages: catalog-service
answers 401 for server errors (1), order-service's order-dispatched consumer stops for good on its
first error (2), and a broker outage leaves orphaned and duplicated orders (3). The fourth is
catalog-service's preStop hook, which can't run, so rollouts drop requests (4).

The Medium findings are mostly about the development and CI setup. The new CI MicroK8s job failed
because Keycloak ran out of memory (5, now fixed), RabbitMQ on Kubernetes is OOM-killed (6), and
catalog's OpenTelemetry agent tries to export logs nobody receives (7). The rest are a destructive
default profile (8), a compose gap that only shows on Docker Engine (9), the smoke test's
robustness (10, 11), Tempo's demo configuration (12), the edge smoke job's stalls, which
came from Podman's network bridge (34), and Keycloak cookies that keep a browser from logging in
(35, found later by the browser tests' first step). The Low findings are cleanups.

## Order relative to the dependency update

All components are to be updated, Spring Boot and the JDK above all. First fix what makes the
update's safety net unreliable, and what the update would spread to more services. Leave until
after the update what sits in code the update rewrites, or doesn't depend on versions. Several
findings are version problems that the update itself fixes.

### Fix before the update

- **5:** the CI MicroK8s job was red, and the update needs a green, stable CI to compare against. Fixed in 9d7caae; check it again when Keycloak is updated (21).
- **11, 15, 16:** failures will be frequent during the update. A false PASS, a crashed summary or a missing link to the logs would hide them. All three are fixed.
- **18, 19:** cheap, and they help find the commit that broke something. With 18 unfixed, a push to the default branch cancels the previous run, so an update commit can end up with no result. Both are fixed.
- **6:** RabbitMQ idles at 140 of its 157 MB. A newer RabbitMQ that needs a little more memory would be OOM-killed, and that would look like a regression of the update. Fixed.
- **1, 2:** small fixes, but their regression tests matter most: they show that the behaviour survives the updates of Spring Security, Spring Cloud Gateway and Spring Cloud Stream. Both are fixed.
- **3:** the interim fix (catch the send failure, mark the order) with a test. The transactional outbox can wait until after the update, since it touches the R2DBC and Stream APIs that change. The interim fix is in.
- **4, with 13 in the same files:** Boot 3.5's default builder is the tiny image without a shell. If the other services move to it, their `sh -c "sleep 5"` hooks break as catalog's did. Both are fixed.
- **7:** once the other services move to agent 2.x, they all start exporting logs. Set `OTEL_LOGS_EXPORTER=none` and give the agent jar a fixed name first, so the agent update becomes a single change. Fixed.
- **8:** one line, and it keeps a `java -jar` during update testing from wiping the catalog. Fixed.
- **10:** only if smoke tests run locally next to other worktrees during the update. They will: the worktrees proceed independently and may start smoke tests at the same time. Fixed.
- **34:** the edge smoke job failed in about one CI run in four, which would blur CI's results during the update. Fixed.

- **21:** PostgreSQL 17 and Keycloak 26. PostgreSQL 14 reaches end of life on 2026-11-12. Fixed ahead of the rest, on 2026-10-28, since it only changes versions in the deployments and tests.

## High

### 1. catalog-service answers 401 for server errors

- **Problem:** `catalog-service/src/main/java/.../config/SecurityConfig.java` ends with `anyRequest().hasRole("employee")`. Spring Security 6 applies it to error dispatches too, and `/error` isn't permitted. So every error response to an anonymous request becomes 401 with `WWW-Authenticate: Bearer`: `GET /books/` (404), `GET /books/%` (400), and, with PostgreSQL down, `GET /books` (5xx). Customers get 403.
- **Effect:** outages look like authentication failures to the SPA and to monitoring. Through edge-service the browser gets the same 401. Edge's Retry filter only retries 5xx, and its catalog circuit breaker counts the 401s as successful calls and never opens. Edge logs nothing. MockMvc tests don't do error dispatches, and the smoke tests don't cover it.
- **Fix:** `.dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()` (or `.requestMatchers("/error").permitAll()`), plus a `RANDOM_PORT` test for `GET /books/` and for a database failure.
- **Fixed:** `SecurityConfig` permits error dispatches, which render a response whose status is already set. A request for `/error` itself still needs the role. `CatalogServiceErrorResponsesTests` starts a real server with an unreachable database, and expects 404 for `GET /books/` and 500 for `GET /books`. Without the fix, both got 401. With it, they pass, and so do catalog's other 46 tests, the 401 and 403 ones included. The 400 for `GET /books/%` goes the same way but isn't tested, since `java.net.URI` rejects such a URL. In CI, run 39312123539's build and its catalog smoke checks passed. Its edge job failed on an order-service health check that doesn't involve this change (see 26).
- **In a browser** (the deferred check, run 2026-10-23 with the browser tests of `development/ui-test/`, on a stack from `smoke-test.sh all edge`):
  - polar-ui's interceptor sends the browser to Keycloak's login page on a 401 from anything but `GET /user`. An anonymous `#/my-orders` did so.
  - With catalog-service's database closed, an employee's "Create Book" got 500 through edge-service, and the page stayed on the form, logged in. Before the fix, catalog's 401 would have sent the employee to log in again.
  - A GET doesn't reach the browser as a 5xx: edge-service's Retry filter repeats it until the circuit breaker's 5 s time limit, and the fallback answers 200 (32).

### 2. order-service's order-dispatched consumer stops on its first error

- **Problem:** `order-service/src/main/java/.../order/event/OrderFunctions.java` subscribes to the flux with `.subscribe()` and no error handling. One error, such as PostgreSQL being down when a message arrives, ends the stream ("onErrorDropped").
- **Effect:** every later order-dispatched message fails with "Dispatcher has no subscribers" and is dropped, so those orders stay ACCEPTED until the service restarts. Readiness and the binder's health stay UP, so nothing restarts it.
- **Fix:** handle errors per message (for example `onErrorResume` with a log inside the per-element pipeline), or use a non-reactive `Consumer`, so the binder's retry and dead-letter queue apply. Add a test with a failing repository.
- **Fixed:**
  - `dispatchOrder` is a non-reactive `Consumer<OrderDispatchedMessage>` that blocks until its order is updated. An error now fails only its own message: the binder tries it three times, logs the failure, drops the message and goes on with the next one.
  - No dead-letter queue: binding one adds arguments to the consumer's queue, and RabbitMQ refuses to redeclare an existing queue with other arguments. It can go with 26, after the update.
  - `OrderDispatchedConsumerTests` sends two order-dispatched messages through the test binder, to a mocked repository that fails to find the first order. Before the fix, that error ended the stream ("onErrorDropped"), and the second message failed with "Dispatcher has no subscribers". With it, the first message was tried three times, and the second order was saved as DISPATCHED. order-service's other 21 tests pass on JDK 17.
  - In CI, run 39313836757 passed the build with the new test, and the order checks in every smoke job. Its edge job failed on the order-service health check, on the stall that is 34.

### 3. A broker outage leaves orphaned and duplicated ACCEPTED orders

- **Problem:** since 81cd148, `OrderService.submitOrder` isn't `@Transactional`. The order is saved and committed before `StreamBridge.send`, which is synchronous and throws when the broker is unreachable.
- **Effect:** with RabbitMQ down, `POST /orders` returns 500 after the 5 s connection timeout, but the order is saved as ACCEPTED and its order-accepted event is never sent. A client retry adds a second ACCEPTED order. The send also blocks the R2DBC event-loop thread for the whole timeout.
- **Fix:** a transactional outbox, or catch the send failure and mark the order (for example with a failed status) or retry the publish. At least document the trade-off in the code and `findings.md`. See 26 for the blocking send.
- **Interim fix:**
  - An order whose order-accepted event can't be sent is saved with the new status FAILED, and returned with 200, as a REJECTED order is. Neither the send's exception nor a `false` result fails the request any more, after the order has been committed. The trade-off is described in `OrderService` and in an open entry of `findings.md`. The outbox is left for after the update, and the blocking send for 26.
  - `OrderAcceptedEventFailureTests` runs against a real PostgreSQL and makes every send on `acceptOrder-out-0` throw `AmqpConnectException`, as the Rabbit binder does with RabbitMQ down. Before the fix, `submitOrder` failed with that exception and left the order ACCEPTED. With it, the order came back FAILED and was stored so. order-service's other 22 tests pass on JDK 17.
  - Locally, on `smoke-test.sh up order` with an image of this tree: with RabbitMQ stopped, `POST /orders` answered 200 with a FAILED order after the 5 s connection timeout, instead of 500, and `GET /orders` listed it as FAILED. Orders sent right after RabbitMQ answered again were FAILED too, at once, until the binder had reconnected. 14 s later they were ACCEPTED and sent.
  - Unexplained, after the first of three outages: order-service's book lookups then hung until BookClient's 3 s timeout, so orders came back REJECTED, until order-service was restarted. catalog-service answered over the same network within milliseconds, no thread was blocked, and aardvark-dns hadn't restarted. Two more outages after the restart didn't repeat it. See the deferred checks. 34 fits it: the restarted RabbitMQ container joined the network again, and if the bridge took its MAC, order-service's lookups of `catalog-service` got no answer.
  - In CI, run 39315799534 passed.

### 4. catalog-service's preStop hook can't run

- **Problem:** `catalog-service/k8s/deployment.yml` runs `sh -c "sleep 5"`, but the image comes from `builder-noble-java-tiny` (since 4dc2ae2), which has no shell. The other services use `builder-jammy-base`, so their hooks work.
- **Effect:** every termination gives a `FailedPreStopHook` event, and the pod stops at once, before it's out of the endpoints. A rolling restart under 20 requests/s failed 2 of about 350 requests.
- **Fix:** `lifecycle.preStop.sleep.seconds: 5`, GA since Kubernetes 1.34. On MicroK8s 1.35 the same rollouts failed no requests. The staging and production overlays use upstream's base, so the fix only reaches them with 33.
- **Fixed:** the preStop hooks of all five deployments use `sleep: seconds: 5`, so none depends on a shell in its image, whichever builder it moves to. kubeconform v0.8.0, run as CI runs it against Kubernetes 1.35.0, accepts the five files, and rejects a copy with a misspelled `sleep` field. The rollout under load wasn't repeated, since MicroK8s wasn't running and starting it needs sudo; the review's run with this hook on MicroK8s 1.35 failed no requests. The smoke tests don't stop pods, so CI only shows that the cluster accepts the manifests and that the pods run. See the deferred checks. In CI, run 39317019809 passed: kubeconform found the manifests valid, and on MicroK8s the four apps rolled out with the new hooks and probe timeouts, with no restarts by the end of its 100 checks.

## Medium

### 5. CI MicroK8s smoke test fails: Keycloak is OOM-killed

- **Problem:** in the first run of the `smoke-k8s` job (run 39222514222, commit 191a277), polar-keycloak was OOM-killed 5 times, about 20 s after each start, at its 750Mi limit (`polar-deployment/kubernetes/platform/development/services/keycloak.yml`). The job and the run failed; the apps were fine. In a container, Keycloak 24's `kc.sh` gives the heap 70% of the memory the JVM sees (`-XX:MaxRAMPercentage=70 -XX:InitialRAMPercentage=50`).
- **Effect:** CI is red. Keycloak runs at its limit on the development server too (peaks of 710-750 MiB under the same limits), so whether it's killed depends on how far the heap grows. Compose gives Keycloak no limit, so the Podman jobs pass.
- **Fix:** set `JAVA_OPTS_KC_HEAP=-XX:MaxRAMPercentage=50 -XX:InitialRAMPercentage=25 -XX:MinHeapFreeRatio=10 -XX:MaxHeapFreeRatio=20` in the deployment's env. Under the same limits, Keycloak then started as fast, imported the realm and peaked at 609 MiB. Confirm with a few CI runs. Raising the limit would work too, but costs the development server memory.
- **Fixed** in 9d7caae, on `mikkosuonio/development`, with a different cause than assumed above. The image's OpenJDK 17.0.14 didn't detect the container's limit on the runner's kernel 6.17 and sized the heap from the runner's 7.75 GiB: up to 5.4 GiB. The Deployment now passes its limit to the JVM as `JAVA_OPTS_APPEND=-XX:MaxRAM=$(MEMORY_LIMIT)`, from the Downward API, so the heap is at most 526 MiB on the runner as on the development server. See `PolarBookshop/findings.md`. Verified: `smoke-k8s` passed in the four runs since (39226291162, 39228185672, 39234346593 and 39235812153), with no app restarts, and Keycloak was ready within its startup probe's 400 s. The smoke test doesn't count Keycloak's own restarts.

### 6. RabbitMQ in the Kubernetes development setup hangs and is OOM-killed

- **Problem:** in `polar-deployment/kubernetes/platform/development/services/rabbitmq.yml` the limit is 150Mi, and RabbitMQ uses 140 of its 157 MB at idle. `vm_memory_high_watermark.relative = 1.0` sizes its memory alarm from the node's RAM, not the pod's limit, so the alarm can never fire before the kernel OOM-kills it. The ConfigMap mount over `/etc/rabbitmq` also hides `conf.d`, so console logging is lost, and `kubectl logs` shows only the boot banner. The deployment has no probes.
- **Effect:** a single `rabbitmqctl` call in the pod made the broker stop answering for about 1.5 minutes, and then it was OOM-killed. A hung broker isn't restarted. Normal message traffic fits. The smoke test doesn't watch RabbitMQ restarts.
- **Fix:** limit 300Mi, `vm_memory_high_watermark.absolute = 200MiB`, and mount `rabbitmq.conf` and `enabled_plugins` with `subPath`. With it, RabbitMQ reports a 200 MiB limit, logs to the console again, and `rabbitmqctl` finishes in 8 s with a 227 MiB peak. 384Mi with a ~250MiB watermark leaves more room for clients. Add a light probe, such as TCP on 5672, and have the smoke test check RabbitMQ's restarts.
- **Fixed:**
  - Limit 300Mi, `vm_memory_high_watermark.absolute = 200MiB`, and only `rabbitmq.conf` mounted, with `subPath`. The image's own `enabled_plugins` has the same list, so the ConfigMap no longer repeats it.
  - Startup and readiness probes on TCP 5672. The liveness probe asks for `/` from the management plugin's web server instead, since the kernel still accepts TCP connections for a hung broker.
  - The Kubernetes smoke test checks after its tests that no container of the deployments has restarted, RabbitMQ's included.
  - Verified locally under Podman, since MicroK8s wasn't running and starting it needs sudo. RabbitMQ ran with that `rabbitmq.conf` mounted as a single file, a 300 MiB limit and 0.2 CPU:
    - It started in 66 s and set its watermark to "200 MiB (209715200 bytes) of 3814 MiB" total, the server's memory.
    - It logged to the console again, started its 5 plugins, and answered `/` on port 15672 with 200.
    - `rabbitmqctl status` took 7 s and peaked at 251 MiB for the container, and the broker kept answering.
  - The restart check, run against a fake `kubectl` whose RabbitMQ pod had restarted twice, failed only that check.

### 7. catalog-service's OpenTelemetry agent exports logs by default

- **Problem:** catalog-service uses agent 2.20.1, which exports logs over OTLP by default; the other services use 1.33, which doesn't. Tempo doesn't accept logs. The smoke test sets `OTEL_LOGS_EXPORTER=none` (`development/script/smoke-test.sh`), so it can't show this.
- **Effect:** under compose without the observability stack, catalog-service logs "Failed to export logs ... UnknownHostException: tempo" every ~10 s. With Tempo it logs "unknown service ... LogsService".
- **Other problems:**
  - The agent version is hard-coded in the jar path in four places.
  - `kubernetes/applications/catalog-service/production/patch-tracing.yml` isn't listed in the overlay's `kustomization.yml`. The overlay deploys upstream's image, which has agent 1.33.6, and with the patch wired in its JVM doesn't start ("agent library failed to init: instrument").
- **Fix:**
  - Set `OTEL_LOGS_EXPORTER=none` in compose and in the production patch.
  - Package the agent under a fixed name, or use the Paketo OpenTelemetry buildpack.
  - Fix or remove `patch-tracing.yml` together with the overlays' bases (33).
- **Fixed:**
  - The five services with the agent declare it in an `otelAgent` configuration instead of `runtimeOnly`, and `bootJar` adds it to the jar's root as `opentelemetry-javaagent.jar`. There it's off the application's classpath, in the application layer, and Paketo unpacks it to `/workspace/opentelemetry-javaagent.jar`. compose's five `-javaagent` paths use that name, so an agent update only changes `otelVersion`.
  - compose sets `OTEL_LOGS_EXPORTER=none` for the five services, and so do the four production `patch-tracing.yml` files.
  - Left for 33: the production patches still name `BOOT-INF/lib/opentelemetry-javaagent-<version>.jar`, since the upstream images they deploy have it there, and catalog's `patch-tracing.yml` is still missing from its kustomization.
  - Verified locally:
    - The boot jars of catalog-service (Boot 3.5) and config-service (Boot 2.7) have the agent at their root, listed in the application layer of `layers.idx` and missing from `classpath.idx`.
    - A catalog-service image built from this tree ran with compose's agent settings, on a network with PostgreSQL but no tempo. The 2.20.1 agent started from the new path. Without `OTEL_LOGS_EXPORTER`, it logged "Failed to export logs" twice in 60 s, and with `none` not once.
    - The other four images are left to CI's smoke tests, which start every service with compose's `JAVA_TOOL_OPTIONS`.
  - In CI, run 39318234899 passed. Every smoke job started its services with the new agent path, and the observability job found traces from catalog-service, order-service and dispatcher-service in Tempo.

### 8. The `testdata` profile is active by default

- **Problem:** `catalog-service/src/main/resources/application.yml` set `spring.profiles.active: testdata` (since 6314b2d).
- **Effect:** `BookDataLoader` runs `deleteAll()` on any start that doesn't set `SPRING_PROFILES_ACTIVE`, such as the README's `java -jar`.
- **Fix:** remove the setting. bootRun, compose and every Kubernetes overlay already set the profile explicitly.

Verified locally: `java -jar` against a scratch PostgreSQL ran with the default profile and kept a book inserted by hand; with `--spring.profiles.active=testdata`, that book was gone and the two sample books were loaded. catalog's 48 tests pass. In CI, run 39319603861 passed.

### 9. compose: order-service can't resolve `host.docker.internal` on Docker Engine

- **Problem:** in `polar-deployment/docker/docker-compose.yml`, order-service's JWT issuer is at `host.docker.internal`, but unlike catalog-service and edge-service it has no `extra_hosts` entry for it.
- **Effect:** on Docker Engine for Linux every authenticated `/orders` request fails. Podman adds the name to every container by itself, so neither local runs nor the CI smoke tests, which use Podman, show it. The smoke test's `--add-host` (`development/script/smoke-test.sh:247`) is redundant on Podman.
- **Fix:** add `extra_hosts: ["host.docker.internal:host-gateway"]` to order-service.

### 10. The smoke test collides with other worktrees' stacks

- **Problem:** container names, ports, the network, image tags, the Kubernetes namespace and the port-forward port are the same for every worktree.
- **Effect:** podman-compose 1.0.6 recreates a shared service when another worktree's compose file differs. polar-postgres has no volume, so its data is lost. CI isn't affected.
- **Fix:** take a `flock` in the script and document "one stack per machine". Per-worktree names would be the larger change.
- **Fixed:**
  - Runs take turns. Each takes a lock in `~/.local/state/polar-smoke-test/` and waits for the run holding it, saying which worktree and command hold it. A process of its own holds the lock, so that containers and other processes a run leaves behind don't keep it.
  - A lock alone doesn't cover `all` followed by a separate `test` or `down`, since another worktree can take the stack over in between. So `up` and `all` record which worktree started the stack. `test` and `logs` refuse another worktree's stack, and `down` leaves it running unless that worktree has been removed.
  - Nor does it cover the image tags. `up` reused an existing image, so a run could test the code of the worktree that built it. The script now records which worktree built each image, and `up` rebuilds one another worktree built.
  - The script's help and the smoke-test skill describe this. Per-worktree names, which would let stacks run side by side, weren't done: two stacks don't fit in this machine's memory.
  - Verified locally with config-service, with records saying that the development worktree had started the stack and built the image. `all config` took the stack over, rebuilt the image and passed its 18 checks. A `test config` started 5 s later waited 78 s for it, naming the run holding the lock, and then passed. The lock was free while the stack ran, and a second `up` reused the image. With the stack recorded as the development worktree's, `test` and `logs` exited with 2 and `down` left config-service running; with a removed worktree's, `down` removed it. A run waiting for the lock and stopped with SIGTERM wrote its JUnit error case, "stopped during: Waiting for the smoke test lock", and left no lock behind. A run from a second real worktree is among the deferred checks.
  - In CI, run 39370912143's smoke jobs took the lock at once, each on a runner of its own, and printed nothing about it. Four passed, with 80, 80, 39 and 100 checks. The edge job failed on the stall that is 34.

### 11. The smoke test can hang or report a false PASS

- **Problems:**
  - No curl call has `--max-time`, so a hung service hangs the run. In CI it holds the job until its 45-minute timeout.
  - `podman pause catalog-service` (`development/script/smoke-test.sh:846`) isn't undone by the EXIT trap, so an interrupted run leaves catalog paused and the next run hangs.
  - `$WORK/body` is reused, so a failed curl can be checked against the previous response and print a misleading PASS.
  - `.claude/skills/smoke-test/SKILL.md` suggests a 10-minute tool timeout, which can kill a `--rebuild` run midway.
- **Fix:** `--max-time` (and `--connect-timeout`) on every curl; `podman unpause` in the EXIT trap; remove `$WORK/body` before each request; a longer timeout, or a background run, for `--rebuild`.
- **Fixed:**
  - Every curl call in the script goes through a wrapper that adds `--connect-timeout 5 --max-time 30`. `wait_until` counts elapsed time instead of attempts, so a hung service doesn't stretch its waits.
  - The EXIT trap unpauses catalog-service if `test_edge` paused it.
  - The request helpers and the metrics check remove the response file before each request.

### 34. The edge smoke job stalls when the network bridge changes its MAC address

- **Problem:** netavark before 1.9 leaves the MAC address of a network's bridge to the kernel, which gives a bridge the lowest MAC of its ports. The development server and the CI runners have Ubuntu 24.04's netavark 1.4.0. When a container joins with a lower MAC, the bridge takes it, and the containers started before keep sending to the old one. Their packets to the gateway, 10.89.0.1, are dropped: DNS lookups, since aardvark-dns answers there, and connections through it, such as to `host.docker.internal`. Traffic between containers isn't affected. A container recovers when its ARP entry for the gateway expires, up to a minute later, or at its first use after that, which first waits about 10 s.
- **Effect:** the edge smoke job failed in 3 of 13 CI runs (39312123539, 39313836757 and 39370912143). edge-service starts last, about 10 s before the tests.   - netavark 1.9.0's release notes have "bridge: force static mac on bridge interface".

- **Fixed:**

### 35. A browser can't log in through the compose setup's Keycloak

Found on 2026-10-23, after the review, in step 0 of `development/plan/ui-testing.md`.

- **Problem:** the realm in `polar-deployment/docker/keycloak/full-realm-config.json` has `sslRequired: external`. Keycloak 24 decides what is external by the request's host name: `localhost` and `127.0.0.1` are local, `host.docker.internal`, the issuer's host, isn't. For an external request over http it marks its login-session cookies `Secure`, the `AUTH_SESSION_ID_LEGACY` and `KC_RESTART` fallbacks too. Browsers drop `Secure` cookies from an http origin other than localhost.
- **Effect:** logging in to polar-ui through edge-service ends on Keycloak's "Cookie not found. Please make sure cookies are enabled in your browser." (400 on the login form's POST), in headless Chromium 153 and so in any browser. The smoke test's `edge_login` passes the cookies on by hand, so it never showed. Chromium's `--unsafely-treat-insecure-origin-as-secure=http://host.docker.internal:8080` doesn't help. The realm came with Keycloak 24 from upstream (868f4e4, June 2024).
- **Fix:** `sslRequired: none` for the compose realm, which only serves plain http on a development machine. The production realm (`kubernetes/platform/production/keycloak/resources/keycloak-config.yml`) already has `none`, since TLS ends before Keycloak there. The Kubernetes development realm (`kubernetes/platform/development/services/keycloak-config.yml`) has `external` with Keycloak 24 and the issuer host `polar-keycloak`, so it very likely has the same problem; check it when the smoke test runs edge-service on Kubernetes.
- **Fixed** for compose:
  - The realm has `sslRequired: none`. On the running dev Keycloak, with `external` the three cookies were `Secure` for `Host: host.docker.internal:8080`, and with `none` only `AUTH_SESSION_ID`, whose `SameSite=None` requires it, was. The `_LEGACY` copy is then the one the browser keeps.

    - A failed update or removal would get 404, a missing book, not 503, an outage. polar-ui shows neither (39), so the difference is in the responses and edge-service's metrics only.
  - **Fix:**
    - Split the catalog route in `application.yml`. `GET /books` keeps the fallback that answers `[]`; the rest of `/books/**` falls back to an endpoint that answers 503 for every method.
    - Cover the new endpoint in `WebEndpointsTests`.
    - In the smoke test's catalog pause, check `GET /books/{isbn}`, `PUT` and `DELETE`, which also confirms or rules out the 404.
    - Add a browser test for what the edit page shows. The fork's e2e tests already cover the page with a failing `GET /books/{isbn}`, as an expected failure (`test.fail`).
  - **Limit:** polar-ui shows no HTTP errors (39), so after this fix a 503 leaves the edit page on its spinner. That beats a misleading form; showing an error is 39's fix, in the fork.
- **39. polar-ui shows no HTTP errors.**
  - **Problem:** found on 2026-10-28 in the fork's step 6 work, by reading its code (`src/app/*/…component.ts`) and with its e2e tests. No `subscribe` in polar-ui has an error callback, so a failed call only reaches the browser console, through Angular's `ErrorHandler`:
    - `GET /books` (`BookListComponent`): the list shows empty, with no message. Seen in the fork's e2e tests.
    - `GET /books/{isbn}` (`EditBookComponent`): the page shows its spinner for good. Seen in the fork's e2e tests, which mark it `test.fail`.
    - `GET /orders` (`OrderListComponent`): by the same code, an empty list. Not tested.
    - The writes: a failed DELETE leaves the book on the list; a failed PUT or POST leaves the form; a failed `POST /orders` leaves the order dialog open. None shows a message. Not tested in a browser.
  - **Effect:** an outage or a rejected write looks like an empty catalog, a slow page or a button that does nothing. Users may retry, or think the request went through.
  - **Fix:** in the fork mikkosuonio-ai/polar-ui, an error callback for each call, with a message, for example a `MatSnackBar`, and on the edit page in place of the spinner. Then remove the `test.fail` from the fork's edit page test; its message has to match `/can't be loaded|cannot be loaded|try again/i`, or the test changes. Add e2e tests for the failing writes. A release of the fork follows, and a tag bump here.
- **40. polar-ui's "My Orders" formats totals with `toPrecision(4)`.**
  - **Problem:** found on 2026-10-28 in the fork's step 6 work. `order-list.component.html` shows `(order.bookPrice * order.quantity).toPrecision(4)`, which gives four significant digits, not two decimals.
  - **Effect:** a total of $9.90 shows as `$9.900`, $1234.50 as `$1235`, and from $10,000 up the total is in exponential notation. The fork's e2e tests pin this behaviour.
  - **Fix:** in the fork, Angular's `currency` pipe (or `toFixed(2)`), and change those e2e tests with it.
- **41. polar-ui has a dead source file that doesn't compile.**
  - **Problem:** found on 2026-10-28 in the fork's step 6 work. `src/app/fake-data.ts` sets `publishingYear`, which `Book` in `types.ts` doesn't have, so it wouldn't compile. Nothing imports it, so the build leaves it out.
  - **Fix:** in the fork, delete it, before the Angular update, so that a stricter compile or a wider `include` doesn't trip on it.
- **42. Production's Keycloak can't be deployed, and deploys differently from development.**
  - **Problem:** found on 2026-10-29 while fixing 21.
    - `kubernetes/platform/production/keycloak/deploy.sh` installs Bitnami's Helm chart 21.4.1 with `values.yml`'s image tag 24.0.5. Broadcom stopped Bitnami's free images in 2025: on Docker Hub, `docker.io/bitnami/keycloak` has no tags left, and `24.0.5` is only in `docker.io/bitnamilegacy`, which gets no updates (checked on 2026-10-29). Newer Bitnami charts need Broadcom's paid images.
    - By default the chart also deploys its own PostgreSQL, from Bitnami's images too. Not checked.
    - Everywhere else Keycloak runs from the official `quay.io/keycloak` image, 26.8.1 since 21's fix: development from plain manifests (`development/services/keycloak.yml`), compose as a container. Both run `start-dev`. So production differs from everything tested in image, packaging and version.
    - The realm is in three copies: compose's `docker/keycloak/`, and development's and production's `keycloak-config.yml`. Production's sets `sslRequired: none`, development's `external`.
  - **Effect:** `deploy.sh` would fail to pull Keycloak's image, so production can't get a working Keycloak as it is. Deduced from the registry, not run.
  - **Fix:** one way to deploy Keycloak in development and production, with the official image. To be decided; the options:
    - **Kustomize, with the development manifests as the base** (recommended on 2026-10-29). Each environment gets an overlay; production's switches to `start` with a database, and adds the hostname, the secrets, its resources and the LoadBalancer. No new tool: the apps' `k8s/` and the smoke script already use Kustomize. CI's MicroK8s job tests the base, and CI could build the production overlay and check it with kubeconform.
    - **The Keycloak Operator,** the Keycloak project's own way, with `Keycloak` and `KeycloakRealmImport` resources. Production already uses an operator for RabbitMQ. But the operator is one more pod on the 4 GB development server, development then needs a database for Keycloak too, and the smoke script and CI have to install it.
    - **One Helm chart everywhere,** such as codecentric's `keycloakx`, which uses the official image. It adds Helm to the smoke script and CI just for Keycloak.
    - With any of them, Kubernetes gets one copy of the realm, and compose's copy is generated from it or checked against it.
