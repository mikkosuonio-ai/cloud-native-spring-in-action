# Review findings for PolarBookshop

Findings from a review of `mikkosuonio/development` from fb268d7 up to 191a277, with proposed
fixes, in priority order. File paths are relative to `PolarBookshop/` unless they start with
`development/` or `.github/`.

## Summary

Four findings are High. Three are application bugs that lose data or hide outages: catalog-service
answers 401 for server errors (1), order-service's order-dispatched consumer stops for good on its
first error (2), and a broker outage leaves orphaned and duplicated orders (3). The fourth is
catalog-service's preStop hook, which can't run, so rollouts drop requests (4).

The Medium findings are mostly about the development and CI setup. The new CI MicroK8s job failed
because Keycloak ran out of memory (5, now fixed), RabbitMQ on Kubernetes is OOM-killed (6), and
catalog's OpenTelemetry agent tries to export logs nobody receives (7). The rest are a destructive
default profile (8), a compose gap that only shows on Docker Engine (9), the smoke test's
robustness (10, 11), and Tempo's demo configuration (12). The Low findings are cleanups.

## Order relative to the dependency update

All components are to be updated, Spring Boot and the JDK above all. First fix what makes the
update's safety net unreliable, and what the update would spread to more services. Leave until
after the update what sits in code the update rewrites, or doesn't depend on versions. Several
findings are version problems that the update itself fixes.

### Fix before the update

- **5:** the CI MicroK8s job was red, and the update needs a green, stable CI to compare against. Fixed in 9d7caae; check it again when Keycloak is updated (21).
- **11, 15, 16:** failures will be frequent during the update. A false PASS, a crashed summary or a missing link to the logs would hide them. All three are fixed.
- **18, 19:** cheap, and they help find the commit that broke something. With 18 unfixed, a push to the default branch cancels the previous run, so an update commit can end up with no result.
- **6:** RabbitMQ idles at 140 of its 157 MB. A newer RabbitMQ that needs a little more memory would be OOM-killed, and that would look like a regression of the update.
- **1, 2:** small fixes, but their regression tests matter most: they show that the behaviour survives the updates of Spring Security, Spring Cloud Gateway and Spring Cloud Stream.
- **3:** the interim fix (catch the send failure, mark the order) with a test. The transactional outbox can wait until after the update, since it touches the R2DBC and Stream APIs that change.
- **4, with 13 in the same files:** Boot 3.5's default builder is the tiny image without a shell. If the other services move to it, their `sh -c "sleep 5"` hooks break as catalog's did.
- **7:** once the other services move to agent 2.x, they all start exporting logs. Set `OTEL_LOGS_EXPORTER=none` and give the agent jar a fixed name first, so the agent update becomes a single change.
- **8:** one line, and it keeps a `java -jar` during update testing from wiping the catalog.
- **10:** only if smoke tests run locally next to other worktrees during the update.

### Fix as part of the update

- **14:** remove the Testcontainers pins and let Spring Boot manage the version.
- **21:** PostgreSQL 17 and Keycloak 26. PostgreSQL 14 reaches end of life on 2026-11-12.
- **22:** goes away with Boot 3. It only matters if the JDK is updated first.
- **25:** the Gradle 9 and Spring Security deprecations.
- **29:** a preset `JAVA_HOME` once every project is on one JDK.
- **12:** trim `tempo.yml` when Tempo and Loki are updated. The usage-reporting opt-outs are one line each and can go in before.

- **3's outbox, 26:** they touch the R2DBC and Stream APIs that change.

## High

### 1. catalog-service answers 401 for server errors

- **Problem:** `catalog-service/src/main/java/.../config/SecurityConfig.java:22-26` ends with `anyRequest().hasRole("employee")`. Spring Security 6 applies it to error dispatches too, and `/error` isn't permitted. So every error response to an anonymous request becomes 401 with `WWW-Authenticate: Bearer`: `GET /books/` (404), `GET /books/%` (400), and, with PostgreSQL down, `GET /books` (5xx). Customers get 403.
- **Effect:** outages look like authentication failures to the SPA and to monitoring. Through edge-service the browser gets the same 401. Edge's Retry filter only retries 5xx, and its catalog circuit breaker counts the 401s as successful calls and never opens. Edge logs nothing. MockMvc tests don't do error dispatches, and the smoke tests don't cover it.
- **Fix:** `.dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()` (or `.requestMatchers("/error").permitAll()`), plus a `RANDOM_PORT` test for `GET /books/` and for a database failure.

### 2. order-service's order-dispatched consumer stops on its first error

- **Problem:** `order-service/src/main/java/.../order/event/OrderFunctions.java:20-22` subscribes to the flux with `.subscribe()` and no error handling. One error, such as PostgreSQL being down when a message arrives, ends the stream ("onErrorDropped").
- **Effect:** every later order-dispatched message fails with "Dispatcher has no subscribers" and is dropped, so those orders stay ACCEPTED until the service restarts. Readiness and the binder's health stay UP, so nothing restarts it.
- **Fix:** handle errors per message (for example `onErrorResume` with a log inside the per-element pipeline), or use a non-reactive `Consumer`, so the binder's retry and dead-letter queue apply. Add a test with a failing repository.

### 3. A broker outage leaves orphaned and duplicated ACCEPTED orders

- **Problem:** since 81cd148, `OrderService.submitOrder` isn't `@Transactional`. The order is saved and committed before `StreamBridge.send`, which is synchronous and throws when the broker is unreachable.
- **Effect:** with RabbitMQ down, `POST /orders` returns 500 after the 5 s connection timeout, but the order is saved as ACCEPTED and its order-accepted event is never sent. A client retry adds a second ACCEPTED order. The send also blocks the R2DBC event-loop thread for the whole timeout.
- **Fix:** a transactional outbox, or catch the send failure and mark the order (for example with a failed status) or retry the publish. At least document the trade-off in the code and `findings.md`. See 26 for the blocking send.

### 4. catalog-service's preStop hook can't run

- **Problem:** `catalog-service/k8s/deployment.yml:25-28` runs `sh -c "sleep 5"`, but the image comes from `builder-noble-java-tiny` (since 4dc2ae2), which has no shell. The other services use `builder-jammy-base`, so their hooks work.
- **Effect:** every termination gives a `FailedPreStopHook` event, and the pod stops at once, before it's out of the endpoints. A rolling restart under 20 requests/s failed 2 of about 350 requests.
- **Fix:** `lifecycle.preStop.sleep.seconds: 5`, GA since Kubernetes 1.34. On MicroK8s 1.35 the same rollouts failed no requests. The staging and production overlays use upstream's base, so the fix only reaches them with 33.

## Medium

### 5. CI MicroK8s smoke test fails: Keycloak is OOM-killed

- **Problem:** in the first run of the `smoke-k8s` job (run 39222514222, commit 191a277), polar-keycloak was OOM-killed 5 times, about 20 s after each start, at its 750Mi limit (`polar-deployment/kubernetes/platform/development/services/keycloak.yml`). The job and the run failed; the apps were fine. In a container, Keycloak 24's `kc.sh` gives the heap 70% of the memory the JVM sees (`-XX:MaxRAMPercentage=70 -XX:InitialRAMPercentage=50`).
- **Effect:** CI is red. Keycloak runs at its limit on the development server too (peaks of 710-750 MiB under the same limits), so whether it's killed depends on how far the heap grows. Compose gives Keycloak no limit, so the Podman jobs pass.
- **Fix:** set `JAVA_OPTS_KC_HEAP=-XX:MaxRAMPercentage=50 -XX:InitialRAMPercentage=25 -XX:MinHeapFreeRatio=10 -XX:MaxHeapFreeRatio=20` in the deployment's env. Under the same limits, Keycloak then started as fast, imported the realm and peaked at 609 MiB. Confirm with a few CI runs. Raising the limit would work too, but costs the development server memory.
- **Fixed** in 9d7caae, on `mikkosuonio/development`, with a different cause than assumed above. The image's OpenJDK 17.0.14 didn't detect the container's limit on the runner's kernel 6.17 and sized the heap from the runner's 7.75 GiB: up to 5.4 GiB. The Deployment now passes its limit to the JVM as `JAVA_OPTS_APPEND=-XX:MaxRAM=$(MEMORY_LIMIT)`, from the Downward API, so the heap is at most 526 MiB on the runner as on the development server. See `PolarBookshop/findings.md`. Verified: `smoke-k8s` passed in the four runs since (39226291162, 39228185672, 39234346593 and 39235812153), with no app restarts, and Keycloak was ready within its startup probe's 400 s. The smoke test doesn't count Keycloak's own restarts.

### 6. RabbitMQ in the Kubernetes development setup hangs and is OOM-killed

- **Problem:** in `polar-deployment/kubernetes/platform/development/services/rabbitmq.yml` the limit is 150Mi, and RabbitMQ uses 140 of its 157 MB at idle. `vm_memory_high_watermark.relative = 1.0` sizes its memory alarm from the node's RAM, not the pod's limit, so the alarm can never fire before the kernel OOM-kills it. The ConfigMap mount over `/etc/rabbitmq` also hides `conf.d`, so console logging is lost, and `kubectl logs` shows only the boot banner. The deployment has no probes.
- **Effect:** a single `rabbitmqctl` call in the pod made the broker stop answering for about 1.5 minutes, and then it was OOM-killed. A hung broker isn't restarted. Normal message traffic fits. The smoke test doesn't watch RabbitMQ restarts.
- **Fix:** limit 300Mi, `vm_memory_high_watermark.absolute = 200MiB`, and mount `rabbitmq.conf` and `enabled_plugins` with `subPath`. With it, RabbitMQ reports a 200 MiB limit, logs to the console again, and `rabbitmqctl` finishes in 8 s with a 227 MiB peak. 384Mi with a ~250MiB watermark leaves more room for clients. Add a light probe, such as TCP on 5672, and have the smoke test check RabbitMQ's restarts.

### 7. catalog-service's OpenTelemetry agent exports logs by default

- **Problem:** catalog-service uses agent 2.20.1, which exports logs over OTLP by default; the other services use 1.33, which doesn't. Tempo doesn't accept logs. The smoke test sets `OTEL_LOGS_EXPORTER=none` (`development/script/smoke-test.sh:233`), so it can't show this.
- **Effect:** under compose without the observability stack, catalog-service logs "Failed to export logs ... UnknownHostException: tempo" every ~10 s. With Tempo it logs "unknown service ... LogsService".
- **Other problems:**
  - The agent version is hard-coded in the jar path in four places.
  - `kubernetes/applications/catalog-service/production/patch-tracing.yml` isn't listed in the overlay's `kustomization.yml`. The overlay deploys upstream's image, which has agent 1.33.6, and with the patch wired in its JVM doesn't start ("agent library failed to init: instrument").
- **Fix:**
  - Set `OTEL_LOGS_EXPORTER=none` in compose and in the production patch.
  - Package the agent under a fixed name, or use the Paketo OpenTelemetry buildpack.
  - Fix or remove `patch-tracing.yml` together with the overlays' bases (33).

### 8. The `testdata` profile is active by default

- **Problem:** `catalog-service/src/main/resources/application.yml:30-31` sets `spring.profiles.active: testdata` (since 6314b2d).
- **Effect:** `BookDataLoader` runs `deleteAll()` on any start that doesn't set `SPRING_PROFILES_ACTIVE`, such as the README's `java -jar`.
- **Fix:** remove the setting. bootRun, compose and every Kubernetes overlay already set the profile explicitly.

### 9. compose: order-service can't resolve `host.docker.internal` on Docker Engine

- **Problem:** in `polar-deployment/docker/docker-compose.yml`, order-service's JWT issuer is at `host.docker.internal`, but unlike catalog-service and edge-service it has no `extra_hosts` entry for it.
- **Effect:** on Docker Engine for Linux every authenticated `/orders` request fails. Podman adds the name to every container by itself, so neither local runs nor the CI smoke tests, which use Podman, show it. The smoke test's `--add-host` (`development/script/smoke-test.sh:247`) is redundant on Podman.
- **Fix:** add `extra_hosts: ["host.docker.internal:host-gateway"]` to order-service.

### 10. The smoke test collides with other worktrees' stacks

- **Problem:** container names, ports, the network, image tags, the Kubernetes namespace and the port-forward port are the same for every worktree.
- **Effect:** podman-compose 1.0.6 recreates a shared service when another worktree's compose file differs. polar-postgres has no volume, so its data is lost. CI isn't affected.
- **Fix:** take a `flock` in the script and document "one stack per machine". Per-worktree names would be the larger change.

### 11. The smoke test can hang or report a false PASS

- **Problems:**
  - No curl call has `--max-time`, so a hung service hangs the run. In CI it holds the job until its 45-minute timeout.
  - `podman pause catalog-service` (`development/script/smoke-test.sh:846`) isn't undone by the EXIT trap, so an interrupted run leaves catalog paused and the next run hangs.
  - `$WORK/body` is reused, so a failed curl can be checked against the previous response and print a misleading PASS.
  - `.claude/skills/smoke-test/SKILL.md` suggests a 10-minute tool timeout, which can kill a `--rebuild` run midway.
- **Fix:** `--max-time` (and `--connect-timeout`) on every curl; `podman unpause` in the EXIT trap; remove `$WORK/body` before each request; a longer timeout, or a background run, for `--rebuild`.
- **Fixed:**
  - Every curl call in the script goes through a wrapper that adds `--connect-timeout 5 --max-time 30`. `wait_until` counts elapsed time instead of attempts, so a hung service doesn't stretch its waits.
  - The EXIT trap unpauses catalog-service if `test_edge` paused it.
  - The request helpers and the metrics check remove the response file before each request.
  - The skill runs builds in the background.
  - Verified locally with catalog-service: `all catalog` passed its 23 checks. With catalog-service paused, `test catalog` ended after 8.5 minutes with 23 FAILs instead of hanging. Against a fake edge-service that stops answering after the logout, the four hung requests failed after 30 s each, "books returned again" failed instead of passing on the previous response, and catalog-service was unpaused at the end. Killing that run with SIGTERM while catalog-service was paused left it running.
  - Verified in CI run 39278264347: on its second attempt all five smoke jobs passed, with 93 checks on MicroK8s, 80 on the default services, 80 with observability, 87 on edge and 39 on the quote services. The first attempt failed in the MicroK8s install (see 19), before the smoke test.
  - "fallback body is empty" still passes on a failed request, since it expects an empty body. The status check before it fails, and 32 changes that body.

### 12. `tempo.yml` is Grafana's demo config, and Tempo and Loki report usage

- **Problems:**
  - `polar-deployment/docker/observability/tempo/tempo.yml` points at a memcached server that compose doesn't define, which gives a DNS error and a warning every minute.
  - It turns on cost attribution, demo retention and the local-blocks processor, which cost memory.
  - It dropped `usage_report.reporting_enabled: false`, so Tempo reports usage to Grafana Labs. It now does so from every CI run.
  - compose gives Loki no config, and the image's default leaves its `analytics` module on.
- **Fix:**
  - Trim `tempo.yml` to what the stack uses.
  - Restore the usage-report opt-out.
  - Start Loki with `-reporting.enabled=false`, or give it a config.
  - Bind the OTLP receivers explicitly to `0.0.0.0:4317` and `0.0.0.0:4318`. Tempo has needed the explicit endpoint since 2.7.

## Low

- **13. Liveness probes keep a 1 s timeout.**
  - **Problem:** the startup probes (62b4aa3) stop the restarts during slow starts. After startup, though, three slow liveness answers in a row (15 s) under CPU starvation still restart a container.
  - **Fix:** `timeoutSeconds: 3` on the liveness and startup probes of the five `k8s/deployment.yml` files. With 0.25 CPU, the startup probe and a 3 s liveness timeout together gave no restarts.
- **14. Testcontainers is too old for `ubuntu-26.04` runners.**
  - **Problem:** CI runs on `ubuntu-24.04` (Docker 28) and passes. `ubuntu-26.04` ships Docker 29, whose minimum API is 1.44, and `ubuntu-latest` moves to it in November 2026 ([runner-images#14748](https://github.com/actions/runner-images/issues/14748)). There, Testcontainers before 1.21.4 fails with "client version 1.32 is too old"; catalog pins 1.21.3, and order and edge pin 1.19.8. The per-service workflows under `*/.github/workflows`, which don't run in this repository, and the disabled `native-build` job still use `ubuntu-22.04`. Those runners are unsupported from 2027-04-17 ([runner-images#14254](https://github.com/actions/runner-images/issues/14254)).
  - **Fix:** upgrade to Testcontainers 1.21.4 (or 2.0.2+) before moving to `ubuntu-26.04`; 1.21.4 works with the local Podman 4.9. Use `ubuntu-24.04` in any per-service workflow that gets used.
- **15. The CI summary crashes when listing the artifacts fails.**

  - **Fix:** empty the file in the `||` branch, or skip lines without a tab.
  - **Fixed:** the step empties `artifacts.tsv` in the `||` branch, which also drops a listing that fails after some pages. Verified locally by running the step's shell text under `bash -e`, as the runner does: against a run that doesn't exist, the old text left the 404 response in the file and `report-summary.py` failed with `ValueError`. The new one left the file empty, gave the warning, and the summary printed its table without links. Against run 39235812153, it listed the 12 report artifacts and the rows had their links. In CI, run 39294818027 listed them without the warning and wrote the summary with its links.
- **16. The CI summary gives no link for a row without test results.**

  - **Fixed:** the script looks up the link first and prints it in that row too. - **18. cancel-in-progress also cancels default-branch and scheduled runs.**
  - **Problem:** the concurrency group is the workflow and ref for every event (`.github/workflows/commit-stage.yml`). A second push to `mikkosuonio/development` cancels the first push's run, and the Monday run and a push run cancel each other.
  - **Fix:** cancel only for pushes to other branches, for example `cancel-in-progress: ${{ github.ref != format('refs/heads/{0}', github.event.repository.default_branch) }}`, or put `github.event_name` into the group.

A push to the default branch, a scheduled run and a manual run each add their run id to the group, so nothing cancels them. A conditional `cancel-in-progress` alone wouldn't have been enough: with the shared group, a run that queues while another runs still cancels the one pending before it.

    - Under Podman the apps' logs can't reach fluent-bit, because Podman 4.9 has no `fluentd` log driver.
    - The smoke test checks neither Loki nor fluent-bit.
    - Exemplars are dropped because Prometheus' exemplar storage is off.
    - The native-histograms flag is experimental.
  - **Fix:** turn on exemplar storage if exemplars are wanted, and add Loki checks to the observability smoke test.
- **29. The smoke test hard-codes JDK versions.**
  - **Problem:** the default JDKs are exact sdkman versions (`development/script/smoke-test.sh:77-79`), though `SMOKE_JDK_17` and `SMOKE_JDK_21` can override them.
  - **Fix:** a preset `JAVA_HOME` once every project is on one JDK, as planned.
- **30. The README doesn't mention cleaning up after Testcontainers without Ryuk.**
  - **Problem:** the Podman/Testcontainers section disables Ryuk, which normally removes the test containers, but doesn't say they must then be removed by hand.
  - **Fix:** add a note on removing them.
- **31. `PUT /books/{isbn}` for a missing book uses the body's ISBN.**
  - **Problem:** the request creates the book with the body's ISBN, not the path's. This is untested.
  - **Fix:** use the path's ISBN, or reject a mismatch, and add a test.
- **32. edge-service's catalog fallback returns an empty string.**
  - **Problem:** whenever the circuit breaker opens, the SPA gets 200 with an empty string body for `GET /books`, not a JSON list. The edge smoke test asserts the empty body.
  - **Fix:** return an empty JSON list, and change the smoke check with it.
- **33. Kustomize overlays use a deprecated field and upstream bases.**
  - **Problem:** every staging and production overlay uses `patchesStrategicMerge`, which kustomize reports as deprecated. Their bases are the book's upstream repositories (`github.com/polarbookshop/<service>/k8s?ref=main`), so fixes to this repository's `k8s/` don't reach them, and CI can't validate them.
  - **Fix:** run `kustomize edit fix` to convert to `patches`, and point the bases at this repository's `k8s/` directories.
