## High

1. **catalog-service's Kubernetes preStop hook can't run** [run].
   - **Problem:** `catalog-service/k8s/deployment.yml:25-28` runs `sh -c "sleep 5"`, but since 4dc2ae2 the image comes from `builder-noble-java-tiny`, which has no shell. The image has no `ls` either. Boot 3.5's default builder is the same tiny image. The other four services use `builder-jammy-base`, which has a shell, so their identical hooks work.
   - **Effect** [run]: every termination gives `FailedPreStopHook`, and the pod was gone 1.5 s after the scale-down. A `rollout restart` under 20 requests/s failed 2 of 343 and 2 of 351 requests (connection errors at the moment the old pod stopped).
   - **Fix** [run]: `lifecycle.preStop.sleep.seconds: 5`, GA since Kubernetes 1.34 (MicroK8s here is 1.35). With it there is no hook event, graceful shutdown starts 5.3 s after the stop, and the same rollouts failed 0 of 363 and 0 of 368 requests.
   - **Caveat:** the staging and production overlays use upstream's `k8s` base (`github.com/polarbookshop/catalog-service/k8s?ref=main`), so a fix here doesn't reach them.
   - Round 4: neither kubeconform nor the CI MicroK8s job can catch this. The job deploys catalog once and never stops a pod, and the hook's failure is only an event.

2. **catalog-service: Spring Security 6 applies `anyRequest().hasRole("employee")` to error dispatches** [run]. `SecurityConfig.java:22-26` doesn't permit `/error`.
   - Anonymous `GET /books/` returns 401 with `WWW-Authenticate: Bearer` instead of 404.
   - `GET /books/%` returns 401 instead of 400.
   - **With PostgreSQL stopped, anonymous `GET /books` returns 401 instead of 5xx.** Server outages look like authentication failures to the SPA, to edge-service's circuit breaker and to monitoring. Customers get 403.
   - **Through edge-service** [run]: the browser gets the same 401 with `WWW-Authenticate: Bearer`, after 2 s. Edge sends one request (its Retry filter retries only 5xx), the catalog circuit breaker counts every such call as *successful* (16 of 16) and stays closed, and edge logs nothing. With catalog-service itself down, by contrast, the circuit breaker opened after 10 failures and the fallback answered in 5 ms.
   - MockMvc tests don't do error dispatches, so nothing caught it. The smoke tests, now also in CI, don't stop PostgreSQL or ask for a missing book anonymously.
   - **Fix:** `.dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()` (or `.requestMatchers("/error").permitAll()`), plus a `RANDOM_PORT` test for `/books/`.

3. **order-service: a failed order-accepted publish leaves an orphaned ACCEPTED order** [run]. Since 81cd148, `submitOrder` isn't `@Transactional`.
   - `StreamBridge.send` is synchronous and throws on broker failure. The Rabbit binder 3.2.10 handler is an `AmqpOutboundEndpoint` with a channel-transacted `RabbitTemplate`.
   - `SimpleR2dbcRepository.save` has already committed by then. Before 81cd148 the error rolled the save back.
   - [run] With `polar-rabbitmq` stopped, `POST /orders` returned 500 after 5.1 s (`AmqpIOException: Connect timed out`), and the order was in the table as ACCEPTED. The retry returned 500 too and added a second ACCEPTED row. No order-accepted event is ever sent for either.
   - [run] The send blocks the R2DBC event-loop thread (`reactor-tcp-epoll-1`) for the whole 5 s connection timeout (see #18).
   - Neither the code comment nor findings.md mentions this trade-off.
   - **Fix:** a transactional outbox, or catch the send failure and mark or retry the order. At least document it.

    - Cause [static]: in a container, Keycloak 24.0.5's `kc.sh` sets `-XX:MaxRAMPercentage=70 -XX:InitialRAMPercentage=50` with ParallelGC. The heap may take 525Mi of the 750Mi, while metaspace alone may grow to 256m, and code cache and threads come on top.
    - [run] Under Podman with the same limits and the realm import, it started without an OOM kill (after ~150 s at 0.5 CPU), but the cgroup's peak reached 750 and 710 MiB. At most 443 MiB of that was anonymous memory; the rest was page cache the kernel could reclaim. So Keycloak runs at its limit everywhere, and how far its heap grows decides whether it's killed [likely]. The Podman jobs pass because compose gives Keycloak no limit, and the development server's cold `all --k8s` (62b4aa3) passed with the same manifest.
    - The run's JUnit error case names the wrong step (#33): "stopped during: Deploying dispatcher-service".
    - **Fix:** leave room outside the heap, for example `JAVA_OPTS_KC_HEAP=-XX:MaxRAMPercentage=50 -XX:InitialRAMPercentage=25 -XX:MinHeapFreeRatio=10 -XX:MaxHeapFreeRatio=20` in the deployment's env. [run] With it, Keycloak started as fast, imported the realm, and peaked at 609 MiB with at most 367 MiB anonymous. Whether that makes the CI job reliably green needs a few CI runs. A higher limit would work too, but costs the development server memory.
