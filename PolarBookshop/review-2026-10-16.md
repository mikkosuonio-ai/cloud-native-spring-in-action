## High

1. **catalog-service's Kubernetes preStop hook can't run** [run].
   - **Problem:** `catalog-service/k8s/deployment.yml:25-28` runs `sh -c "sleep 5"`, but since 4dc2ae2 the image comes from `builder-noble-java-tiny`, which has no shell. The image has no `ls` either. Boot 3.5's default builder is the same tiny image.
   - **Effect** [run]: every termination gives `FailedPreStopHook`, and the pod was gone 1.5 s after the scale-down. A `rollout restart` under 20 requests/s failed 2 of 343 and 2 of 351 requests (connection errors at the moment the old pod stopped).
   - **Fix** [run]: `lifecycle.preStop.sleep.seconds: 5`, GA since Kubernetes 1.34 (MicroK8s here is 1.35). With it there is no hook event, graceful shutdown starts 5.3 s after the stop, and the same rollouts failed 0 of 363 and 0 of 368 requests.
   - **Caveat:** the staging and production overlays use upstream's `k8s` base (`github.com/polarbookshop/catalog-service/k8s?ref=main`), so a fix here doesn't reach them.

2. **catalog-service: Spring Security 6 applies `anyRequest().hasRole("employee")` to error dispatches** [run]. `SecurityConfig.java:22-26` doesn't permit `/error`.
   - Anonymous `GET /books/` returns 401 with `WWW-Authenticate: Bearer` instead of 404.
   - `GET /books/%` returns 401 instead of 400.
   - **With PostgreSQL stopped, anonymous `GET /books` returns 401 instead of 5xx.** Server outages look like authentication failures to the SPA, to edge-service's circuit breaker and to monitoring. Customers get 403.
   - **Through edge-service** [run]: the browser gets the same 401 with `WWW-Authenticate: Bearer`, after 2 s. Edge sends one request (its Retry filter retries only 5xx), the catalog circuit breaker counts every such call as *successful* (16 of 16) and stays closed, and edge logs nothing. With catalog-service itself down, by contrast, the circuit breaker opened after 10 failures and the fallback answered in 5 ms.
   - MockMvc tests don't do error dispatches, so nothing caught it.
   - **Fix:** `.dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()` (or `.requestMatchers("/error").permitAll()`), plus a `RANDOM_PORT` test for `/books/`.

3. **order-service: a failed order-accepted publish leaves an orphaned ACCEPTED order** [run]. Since 81cd148, `submitOrder` isn't `@Transactional`.
   - `StreamBridge.send` is synchronous and throws on broker failure. The Rabbit binder 3.2.10 handler is an `AmqpOutboundEndpoint` with a channel-transacted `RabbitTemplate`.
   - `SimpleR2dbcRepository.save` has already committed by then. Before 81cd148 the error rolled the save back.
   - [run] With `polar-rabbitmq` stopped, `POST /orders` returned 500 after 5.1 s (`AmqpIOException: Connect timed out`), and the order was in the table as ACCEPTED. The retry returned 500 too and added a second ACCEPTED row. No order-accepted event is ever sent for either.
   - [run] The send blocks the R2DBC event-loop thread (`reactor-tcp-epoll-1`) for the whole 5 s connection timeout (see #18).
   - Neither the code comment nor findings.md mentions this trade-off.
   - **Fix:** a transactional outbox, or catch the send failure and mark or retry the order. At least document it.

Its deprecation began 2026-09-17, jobs fail during brownouts on March 23 and 30 and April 6 and 13 (2027, 14:00-24:00 UTC), and it's unsupported from 2027-04-17 ([runner-images#14254](https://github.com/actions/runner-images/issues/14254)).
   - **Fix:** move to `ubuntu-24.04` now. Before `ubuntu-26.04` or `ubuntu-latest`, upgrade Testcontainers to 1.21.4 (or 2.0.2+). [run] 1.21.4 works with the local Podman 4.9 (API 1.41): all edge tests passed with it.

5. **The `testdata` profile is active by default** [static]. Since 6314b2d, `application.yml:30-31` makes `BookDataLoader` run `deleteAll()` on any start without `SPRING_PROFILES_ACTIVE`, including the README's `java -jar`. bootRun, compose and every Kubernetes overlay set the profile explicitly. **Fix:** remove `spring.profiles.active` from `application.yml`.

6. **Kubernetes liveness restarts during slow starts** (open in findings.md) [run]. All five `k8s/deployment.yml` files have liveness probes with a 10 s delay and 5 s period, and no startupProbe.
   - [run] catalog limited to 0.25 CPU, standing in for several JVMs starting on 2 CPUs, never became ready: the kill starts ~20 s in, and with the hook and grace period the container was restarted about once a minute (3 restarts in 189 s, 5 in 252 s).
   - **Fix** [run]: a startupProbe (period 5, threshold 30) plus `timeoutSeconds: 3` on liveness. With it the same pod was ready after ~79 s with no restarts. A 3 s timeout on the startupProbe too would be safer.

7. **OTel agent 2.x exports logs by default** [run].
   - When Tempo isn't running (compose without observability), catalog-service (agent 2.20.1) logs "Failed to export logs ... UnknownHostException: tempo" every ~10 s. order-service with agent 1.33.3 doesn't export logs (`none` default).
   - [run] Against a real Tempo, it logs "Failed to export logs: unknown service opentelemetry.proto.collector.logs.v1.LogsService" once at startup and then nothing more (2.5 min with traffic). The agent presumably keeps sending every batch to be rejected [likely]. Traces do arrive.
   - The regression is catalog-only. **Fix:** `OTEL_LOGS_EXPORTER=none` in compose and the production patch.
   - The agent version is also hard-coded in the jar path in four places. 4305b66 already fixed one drift.
   - `production/patch-tracing.yml` isn't listed in `production/kustomization.yml`, and the overlay deploys upstream's image (agent 1.33.6). So the in-range edits there have no effect, and [run] when wired in, the JVM doesn't start ("agent library failed to init: instrument").
   - **Fix:** package the agent under a fixed name, or use the Paketo OpenTelemetry buildpack.

8. **order-service's order-dispatched consumer dies on its first error** (pre-existing; findings.md understates it; High by impact) [run].
   - `OrderFunctions.java:20-22` calls `.subscribe()` with no error handling.
   - [run] An order-dispatched message arriving while PostgreSQL was down ended the stream ("Operator called default onErrorDropped"). After PostgreSQL was back, a new order's order-dispatched message failed with "Dispatcher has no subscribers" and was dropped (the queue stayed empty), so the order stays ACCEPTED. The same happens to every later message until a restart.
   - Readiness and the binder's health stay UP, so nothing restarts the service.
   - **Fix:** per-element `onErrorResume` with a log, or a non-reactive `Consumer` so the binder's retry and DLQ apply.

9. **docker-compose: order-service has no `extra_hosts: host.docker.internal:host-gateway`** [static]. Its JWT issuer uses that host, so on Docker Engine for Linux every authenticated `/orders` request fails. catalog and edge got the entry in this range.
   - [run] Podman 4.9 adds `host.docker.internal` to every container's `/etc/hosts` by itself, so the gap can't show here, and the smoke test's `--add-host` (`smoke-test.sh:188`) is redundant on Podman.

10. **Smoke test vs. concurrent worktrees** [run].
    - Container names, ports, network, image tags, the Kubernetes namespace and the port-forward port are global.
    - podman-compose 1.0.6 recreates a shared service (new container ID) when another worktree's compose file differs. polar-postgres has no volume, so its data goes.
    - **Fix:** take a `flock` and document "one stack per machine". Per-worktree names would be the larger change.

11. **Smoke-test robustness** [run].
    - No curl call has `--max-time`. Against a paused container, curl was still hanging after 20 s.
    - `podman pause catalog-service` (:752) isn't undone by the EXIT trap, so an interrupted run makes the next one hang.
    - `k port-forward … &` backgrounds a shell function, so `$!` is a subshell. [run] With the real `microk8s kubectl`, the EXIT trap's kill left three processes running (two MicroK8s wrapper shells and kubectl) and the port open. So the Keycloak port-forward leaks and holds :38080.
    - **Port-forward fix** [run]: start it with `setsid` and kill the process group (`kill -- -$pid`); that left nothing behind.
    - `$WORK/body` is reused, so a failed curl can be checked against the previous response and print a misleading PASS.
    - SKILL.md's 10-minute tool timeout can kill a `--rebuild` run midway.

12. **`tempo.yml` is Grafana's demo config** [run].
    - It points at a memcached server compose doesn't define. [run] That gives one DNS error and one warning every 60 s; searches add none.
    - It turns on cost attribution, demo retention and the local-blocks processor, which costs memory.
    - It dropped `usage_report.reporting_enabled: false`. [run] Tempo 2.8 starts its `usage-report` module, so it reports usage to Grafana Labs.
    - [run] Loki does the same: compose gives it no config, and the image's default config leaves its `analytics` module on (statistics go to stats.grafana.org).
    - **Fix:** trim it, restore the opt-out, add `-reporting.enabled=false` (or a config) for Loki, and bind `0.0.0.0:4317/4318`. The explicit endpoint is needed since Tempo 2.7.

Idle use is ~150 MiB, so 384Mi with a ~250MiB watermark would leave more headroom for clients.
